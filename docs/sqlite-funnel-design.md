# Retiring the JobHub server: the funnel moves to SQLite

_Design, 2026-08-28. **Status: IMPLEMENTED 2026-09-11.** Tracked as epic
`61ea56a8-868f-4c66-9268-6bc982010061`. (The epic named in the original draft,
`71f34fab-…`, no longer exists — it 404s.)_

**What shipped, and what changed from this design.** `scripts/jobhub_db.py` plus
`scripts/jobhub_db_cases.py` (27 cases). The three call sites are ported. The board list was
re-exported fresh on 2026-09-11 — 110 boards, a strict superset of the 109 in the 08-28 export —
and loaded. Four additions this design did not anticipate:

1. **`$JOBHUB_DB`** redirects the store, so a call site can be exercised without writing test rows
   into the real funnel.
2. **`server/cmd/eval`**, a standalone CLI. The eval engine was the one part of the server still
   earning its keep, and `eval.Engine.Run` turned out to be pure — only the HTTP handler needed
   Postgres. `/job-eval` now runs it locally instead of POSTing.
3. **The scan's rejection filter was reading the superseded server table.** Measured on 2026-09-11:
   8 rejected companies from the API where the records held 11. Three were missing, so their
   postings could resurface in every scan. Now reads `user/applications/`.
4. **`jobhub-api.md` deleted**, replaced by `prompts/reference/jobhub-store.md`. The rule file
   `use-deployed-server.md` was renamed `where-funnel-work-goes.md`, since its old name described a
   thing that no longer exists.

The migration question below was **resolved by option 1, accept the loss**, with boards preserved.

Successor to `state-consolidation-design.md` (2026-08-26), which moved applications, research and
evals to files and left "the funnel" on the server. This removes the server too.

## Why now

`state-consolidation-design.md` kept the server on a sound argument: scan results are
"machine-generated, machine-read, disposable, and far too voluminous for markdown." **That argument
is for a database. It was never an argument for a networked service.**

Two facts settled it on 2026-08-28:

1. **Andre does not use the dashboard.** Asked directly whether the HTML views justified the
   deployment: *"no, just the api really."* The dashboard was the only thing the network boundary
   bought.
2. **The live API surface is three endpoints.** `POST /api/search-results`,
   `POST`+`PATCH /api/fit-reports`, `GET`+`POST /api/boards`. Applications were superseded on
   2026-08-26, research on 2026-08-28. Everything else in `jobhub-api.md` is already marked
   do-not-use.

And a third fact that removes the hard part: **the triage LLM is local Ollama**
(`scripts/triage.py:96`), not a server capability. There is no model dependency to replace.

### The cost of the half-alive server, observed

- `prompts/reference/jobhub-api.md` is roughly half "SUPERSEDED — do not use." It has become an
  archaeology document.
- On 2026-08-28 an agent read `company-research.md` (which still instructed a research POST),
  concluded `use-deployed-server.md` was the stale file, **rewrote a correct rule**, and posted an
  orphan row that cannot be deleted. That failure is only possible because two stores exist.
- Reading a fit report costs a round-trip to discover `GET` returns 405 and `/fit-reports` returns a
  302 to authentik.

**The confusion generated by the surface being kept alive now exceeds the value of the surface being
used.**

## Prior art, and why this is a reversal

`server/cmd/migrate-data/main.go` migrates **SQLite → Postgres**, and `server/jobhub.db` (last
written 2026-07-27) is the file it read. The project ran this exact migration in the opposite
direction in July.

**That is not an argument against reversing it.** The July migration existed to put the dashboard
behind a deployment. The dashboard is the thing being dropped, so its justification goes with it.
Recorded so nobody later reads this as ignorance of the earlier decision.

## Decisions

| Question | Decision |
|---|---|
| Where does the funnel live? | **`user/jobhub.db`**, a SQLite file, gitignored with the rest of `user/`. |
| What talks to it? | **`scripts/jobhub_db.py`**, imported directly. No HTTP, no daemon, no auth. |
| What happens to the Go server? | **Left in the tree, stops being deployed.** Same treatment `state-consolidation-design.md` gave the superseded endpoints. Deleting it is a separate decision. |
| Schema | **Translated verbatim** from `server/migrations/0001_init.up.sql`. Same table and column names, so the Go code stays readable as reference. |
| UUIDs | **Kept.** `str(uuid.uuid4())` in Python. Application records already carry `server_id` values; changing the id shape would orphan them. |
| Timestamps | **ISO-8601 UTC strings**, as the API already returns. SQLite has no timestamptz. |
| `below_floor` | **Dropped.** Already vestigial — there is no comp floor. |
| Concurrency | **WAL mode.** One writer (07:15 launchd), occasional agent reads. Not a contended workload. |

## Schema translation

Five tables carry over. `research_briefs`, `applications`, `application_events` and `eval_results`
are **not** recreated — they moved to files and recreating them would rebuild the problem
`state-consolidation-design.md` solved.

```sql
CREATE TABLE companies (
    id TEXT PRIMARY KEY, name TEXT NOT NULL UNIQUE, slug TEXT NOT NULL UNIQUE,
    created_at TEXT NOT NULL, updated_at TEXT NOT NULL);

CREATE TABLE boards (
    id TEXT PRIMARY KEY, slug TEXT NOT NULL UNIQUE, name TEXT NOT NULL,
    ats TEXT NOT NULL CHECK (ats IN ('greenhouse','lever','ashby')),
    tags TEXT NOT NULL DEFAULT '',
    status TEXT NOT NULL CHECK (status IN ('tracked','discovery','dead')),
    last_probed_at TEXT, created_at TEXT NOT NULL, updated_at TEXT NOT NULL);

CREATE TABLE search_batches (
    id TEXT PRIMARY KEY, ran_at TEXT NOT NULL, board_count INTEGER NOT NULL DEFAULT 0,
    raw_count INTEGER NOT NULL DEFAULT 0, location_filter TEXT, notes TEXT,
    created_at TEXT NOT NULL);

CREATE TABLE search_results (
    id TEXT PRIMARY KEY,
    search_batch_id TEXT NOT NULL REFERENCES search_batches(id) ON DELETE CASCADE,
    company_id TEXT NOT NULL REFERENCES companies(id),
    role_title TEXT NOT NULL, location TEXT, is_remote INTEGER NOT NULL DEFAULT 0,
    salary_min INTEGER, salary_max INTEGER, salary_disclosed INTEGER NOT NULL DEFAULT 0,
    posting_url TEXT NOT NULL,
    fit_tier TEXT NOT NULL CHECK (fit_tier IN ('strong','good')),
    tags TEXT NOT NULL DEFAULT '', level_tag TEXT, domain_tag TEXT, created_at TEXT NOT NULL);

CREATE TABLE fit_reports (
    id TEXT PRIMARY KEY, company_id TEXT NOT NULL REFERENCES companies(id),
    role_title TEXT NOT NULL, location TEXT, level TEXT, posting_url TEXT,
    verdict TEXT NOT NULL CHECK (verdict IN ('strong','worth','stretch','skip')),
    verdict_summary TEXT NOT NULL, why_apply TEXT,
    created_at TEXT NOT NULL, updated_at TEXT NOT NULL);

CREATE TABLE fit_signals (
    id TEXT PRIMARY KEY,
    fit_report_id TEXT NOT NULL REFERENCES fit_reports(id) ON DELETE CASCADE,
    kind TEXT NOT NULL CHECK (kind IN ('match','gap','flag')),
    requirement TEXT NOT NULL, evidence TEXT NOT NULL, source TEXT,
    sort_order INTEGER NOT NULL DEFAULT 0);
```

`research_brief_id` is dropped from `fit_reports` — research is a file now, and the sidebar link it
fed does not exist without a dashboard.

**One deliberate improvement over the server:** `fit_signals` gets a real delete path.
`jobhub-api.md` warns that signal arrays are create-only with no DELETE, so "a wrong one cannot be
removed." That was an HTTP-surface limitation, not a data one. A local module has no reason to
inherit it.

## Module API

`scripts/jobhub_db.py`, mirroring the calls the scripts already make:

```python
connect(path=None)                  # opens user/jobhub.db, WAL, applies schema if absent
upsert_company(conn, name)          # -> company_id, by slug
post_search_results(conn, batch, results)   # -> batch_id
create_fit_report(conn, payload)    # -> fit_report_id, writes signals
patch_fit_report(conn, id, **fields)        # narrative fields
list_boards(conn, status=None)      # -> tracked / discovery
upsert_board(conn, slug, name, ats, tags, status)
```

Return shapes match today's JSON so the call sites change from `curl`+parse to a function call
without reworking their logic.

## Migration — BLOCKED, and this is the open decision

**The existing Postgres data cannot be read out over HTTP.** Probed 2026-08-28:

| Endpoint | GET | |
|---|---|---|
| `/api/boards` | **200** | ✅ exported — 109 tracked boards, `server/export/boards-2026-08-28.json` |
| `/api/search-results` | **405** | write-only |
| `/api/fit-reports` | **405** | write-only |
| `/api/companies` | **404** | no route |
| `/applications`, `/fit-reports` (HTML) | **302** | authentik SSO |

So `boards` — the one genuinely irreplaceable table, being a hand-curated list of 109 slugs — is
**already safe**. The rest needs a decision:

1. **Accept the loss.** `state-consolidation-design.md` calls funnel data "machine-generated,
   machine-read, disposable." Search results regenerate at 07:15 tomorrow. Fit reports are the real
   question: application records were designed to copy the verdict in "as a value, not a URL," so a
   promoted role does not depend on them — but the un-promoted ranking history would go.
2. **Direct Postgres access** — port-forward via the cluster, dump the five tables, load them. Most
   faithful, needs credentials this agent does not have.
3. **Add a temporary export endpoint** to the Go server, deploy, dump, remove. Most work, and it
   means deploying a service being retired.

**Recommendation: (2) if the credentials are cheap to produce, otherwise (1).** Not (3). Andre
decides; nothing is deleted either way, because the Postgres instance keeps running until he says
otherwise.

## Sequence

1. `jobhub_db.py` + schema, with the boards export loaded in.
2. Port `post_results.py`, `fit_batch.py`, `scan.py`.
3. Run the full chain end to end and diff the output against a server run.
4. Update `AGENTS.md`, `jobhub-api.md`, `use-deployed-server.md`, `scripts/launchd/README.md`.
5. Stop deploying the server. Leave the Postgres instance up until a scan cycle has proven the
   replacement.

**`use-deployed-server.md` largely dissolves at step 4.** Most of it — "do not fall back to local,"
"a merged PR is not a deployed PR," "probe the API before running real work" — exists to manage
deployment risk that a local file does not have.
